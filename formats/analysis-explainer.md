# Format — Analysis / explainer

Use when the central task is not merely telling the reader what happened, but making the mechanism intelligible.

## Core engine

**Concrete trigger → proposition → mechanism → evidence → exception/test → consequence.**

The article should leave the reader with a better model, not just more facts.

## Opening options

- a contradiction;
- a number that needs explanation;
- an ordinary object whose behaviour reveals a system;
- a recent event that exposes the mechanism;
- a deceptively simple question.

Avoid broad scene-setters such as "The world is changing".

## Nut graf

State the explanatory problem early. The reader should know what the article is trying to explain even if the answer unfolds gradually.

## Mechanism

Break the explanation into causal steps. Each section should answer a question generated by the previous one.

Prefer:
> A causes B because C; B then changes D.

over:
> There are several important factors to consider.

## Evidence

Use evidence where it changes the model:
- numbers with baselines;
- records;
- expert explanation;
- historical comparison;
- counterexamples;
- real operational details.

Do not stack citations after the fact. Let evidence drive the paragraph.

## Counter-pressure

Test the central explanation against:
- exceptions;
- alternative explanations;
- boundary conditions;
- uncertainty;
- who benefits from a particular framing.

An explainer becomes analysis when it weighs meaning rather than merely describing process.

## Structure options

### Mechanism ladder
example → mechanism → wider implication → test → consequence

### Contradiction
expected result → observed result → explanation → revised model

### Object journey
follow one object/number/decision through the system

### Comparative
case A → case B → what differs → what that difference reveals

## Ending

Land on:
- the consequence of the mechanism;
- the limit of what is known;
- the decision the model clarifies;
- a return to the opening object with changed meaning.

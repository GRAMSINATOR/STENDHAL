# Format — Science / technical journalism

Use when technical findings, experiments, models or engineering mechanisms must become intelligible to a non-specialist without being diluted.

## Core engine

**Concrete question → finding → method/evidence → mechanism → limitation → why it changes the model.**

## Reader model

Assume intelligence, not prior vocabulary.

Introduce specialist terms only when they are needed to think accurately. Define once with a concrete example, then use consistently.

## Claims

For empirical claims, prefer:
- named source/team;
- study or dataset;
- hard number;
- comparator;
- uncertainty or limitation.

Avoid "research shows" without provenance.

## Structure

Useful chassis:
- result → why surprising → how measured → what mechanism may explain it → limits → consequence;
- scene/object → scientific question → evidence ladder → conceptual payoff;
- myth/model → contrary result → new model → boundary conditions.

## Abstraction ladder

Move both directions:
- concrete observation;
- technical explanation;
- conceptual meaning;
- return to observable consequence.

Do not remain at jargon altitude.

## Analogy

Explain the concept first. Use an analogy only if it preserves the important structure. State where the analogy breaks if the break matters.

## Numbers

Give readers a scale they can hold. Avoid strings of raw values without comparison.

## Limitation

A limitation is not a ritual paragraph at the end. Place caveats next to the claims they constrain.

## Ending

Return to the question or phenomenon with a changed model. Avoid claiming a single study "proves" a broad theory.
